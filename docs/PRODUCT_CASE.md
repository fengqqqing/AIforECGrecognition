# ECG AI 辅助识别工作台产品案例

本文档用于把当前 ECG AI 桌面 Demo 整理成一个可用于项目展示的产品案例。它不替代 `docs/PRD.md`、`docs/PRODUCT_EXPERIENCE.md` 或 `docs/TECH_DESIGN.md`，也不新增临床能力承诺；它负责回答：这个产品原型想解决什么问题、面向谁、为什么这样取舍、当前 Demo 能证明什么。

## 1. 产品案例主线

现实 ECG 工作流中，采集、初筛和正式医生判读往往不是同一个环节。采集与初筛人员不承担最终诊断责任，但他们需要在现场判断波形是否有效、导联是否连接、心率是否可读，以及是否存在值得优先转交医生复核的辅助提示。当前项目把这个中间环节作为产品机会，设计成一个面向 ECG 采集与初筛场景的 AI 辅助桌面工作台：先让用户看到可观察的 ECG 波形和基础状态，再把 AI 输出作为正式判读前的辅助提示，最后通过运行指标、摘要和导出文件留下可复盘证据。产品取舍上，本阶段优先做固定 Demo、模型契约、统一处理管线、可追溯导出和保守医学文案，而不是扩展患者管理、医生复核、医院系统集成或教学训练模式。这个案例要证明的不是模型已经达到临床诊断水平，而是一个算法产物如何被包装成“能被人操作、能被解释、能被复盘”的产品原型。它的展示边界是：AI 结果只能作为辅助识别提示，不能作为最终诊断、处置建议或临床验证结论。

## 2. 问题定义

当前产品案例的问题可以定义为：

> 在 ECG 采集完成到医生正式判读之前，一线采集与初筛人员缺少一个轻量、可视、可追溯的工作台来同时确认信号质量、基础状态、AI 辅助提示和本次运行证据。

这个问题不是“医生不会看 ECG”，也不是“AI 要替代医生”。更准确地说，它发生在正式诊断之前：现场人员通常需要先确认采集是否有效、是否有明显异常线索需要优先转交、系统是否真的完成了一次可追溯处理。当前 Demo 的价值正是在这个中间环节建立一个可演示的体验闭环。

## 3. 核心用户与使用场景

核心用户是 ECG 采集与初筛人员，包括心电图室技师、基层或床旁采集人员、需要先看 ECG 但不是心电专科医生的一线医护人员。他们最关心的不是模型结构，而是“当前信号能不能看、导联有没有问题、心率是否可读、AI 是否给出辅助提示、结果能不能交给后续人员复盘”。

重要次级用户是临床研究人员、算法验证协作者和部署维护人员。他们关心固定样例是否可复现、真实模型回放是否跑通、模型契约是否约束输入输出语义，以及导出文件是否能支持复盘。

评审、合作方、公开展示读者或潜在客户决策者是展示对象，而不是产品日常核心用户。他们通过 Demo 判断产品场景、解决方案、边界和继续投入价值是否成立。

## 4. 用户痛点与产品机会

| 用户痛点 | 当前产品机会 | Demo 已有支撑 |
| --- | --- | --- |
| 采集人员需要先判断 ECG 是否有效输入，但传统演示容易直接跳到 AI 结果。 | 把 ECG 波形作为主视觉，让用户先确认信号质量，再理解辅助识别。 | 中央 ECG 波形区、固定样例回放。 |
| 导联脱落或接触异常会让采集失效，但现场不一定能被及时注意到。 | 用独立导联状态卡表达三导联单通道连接、脱落或未知状态。 | `on_lead_status()`、右侧导联状态卡。 |
| 心率是现场高频查看信息，普通文字展示不够醒目。 | 用独立心率卡展示数值和单位，无效时显示 `--`。 | `on_heart_rate()`、右侧心率卡。 |
| 非心电专家需要正式判读前的异常线索，但不能承担最终诊断责任。 | AI 结果卡提供保守辅助识别提示，用于提示是否值得优先关注或转交复核。 | `AI 辅助识别` 卡、`ui_rules.py` 文案规则。 |
| AI 输出容易被误读成临床结论。 | 明确使用“辅助识别 / 辅助提示 / 医生复核”口径。 | README、Demo runbook、UI 结果卡文案。 |
| 一次运行结束后，后续人员难以知道当时发生了什么。 | 保留运行摘要、指标、诊断事件和可回放 ECG 数据。 | `metrics.jsonl`、`diagnosis.csv`、`ecg_replay.csv`、最近摘要。 |
| 对外演示如果依赖临场选择数据，稳定性和可信度不足。 | 用固定 Demo policy 和一键脚本保证可复现展示。 | `run_demo.ps1`、`--demo`、`DEMO_REPLAY_POLICY`。 |

## 5. 解决方案与体验闭环

当前解决方案不是单一 AI 分类器，而是一条从输入、状态、辅助提示到复盘的桌面工作台闭环：

```text
固定样例 ECG / 串口输入
-> 中央 ECG 波形确认信号是否可观察
-> 心率与导联状态确认基础采集状态
-> ECG 窗口累计并触发模型推理
-> AI 辅助识别卡给出正式判读前提示
-> 底部指标证明系统正在处理数据
-> 最近摘要与导出文件支持后续复盘
```

这条路径支撑三类价值：一线用户能完成信号确认和初筛观察，研究或维护人员能复盘链路，展示对象能看到产品从算法到可交互 Demo 的落地方式。

## 6. 功能设计取舍

| 功能 / 方向 | 当前状态 | 取舍原因 | 风险与后续 |
| --- | --- | --- | --- |
| 固定 Demo 与一键启动 | 已做 | 优先降低演示不确定性，让产品旅程稳定可复现。 | 只能代表固定样例路径，不能替代真实现场验证。 |
| ECG 波形、心率、导联状态 | 已做 | 信号质量和基础状态是 AI 辅助提示成立的前提。 | 当前还没有信号质量评分、伪差识别或采集前检查清单。 |
| AI 辅助识别结果卡 | 已做 | 给非心电专家提供正式判读前的结构化提示。 | 当前不展示置信度或解释原因，不能包装成最终诊断。 |
| 模型契约 | 已做 | 避免输入窗口、归一化参数和标签语义在部署侧漂移。 | 替换模型时仍需同步契约和评估记录。 |
| 运行指标、摘要和导出 | 已做 | 让一次运行可复盘，不只停留在界面瞬时结果。 | 当前还不是完整交接报告或医生复核流程。 |
| 真实模型评估指标展示 | 暂缓 | 当前 smoke 只证明链路可用，不能推断医学准确率。 | 后续需要独立测试集、类别级指标和评估文档。 |
| 患者管理 / 病例管理 | 不做 | 当前 V1 不保存真实患者身份信息，也不引入数据库。 | 进入临床产品化前需要权限、审计、脱敏和数据模型。 |
| 医生复核流程 | 暂缓 | 当前重点是正式判读前辅助提示和复盘证据，不闭环医生确认。 | 后续若进入真实临床流程，需要单独设计复核、签名和追踪。 |
| 医院系统集成 | 不做 | 当前是本地 PyQt Demo，不引入 HIS/EMR/PACS。 | 合作落地时需独立技术设计和合规评估。 |
| ECG 回放训练模式 | 暂缓 | 保存与回放能力有潜力支撑训练，但当前缺题目、答案遮罩和学习记录。 | 可作为未来产品机会，不能写成已实现能力。 |

## 7. 产品案例要证明什么

这个产品案例主要证明五件事：

1. **问题定义能力**：能从 ECG 真实工作流中找到采集与正式判读之间的体验空白，而不是只展示模型输出。
2. **用户聚焦能力**：核心用户是 ECG 采集与初筛人员，展示对象不是产品核心用户。
3. **功能取舍能力**：优先做信号确认、辅助提示、指标和导出复盘，暂缓临床系统能力。
4. **工程落地能力**：固定 Demo、模型契约、统一 ECG 管线和真实模型回放让原型可运行、可验证。
5. **边界控制能力**：所有 AI 结果都保持辅助提示口径，不包装为临床诊断、处置建议或医学准确率验证。

## 8. 展示边界

推荐表达：

- 这是面向 ECG 采集与初筛场景的 AI 辅助桌面工作台原型。
- Demo 展示的是“波形确认 -> 状态观察 -> AI 辅助提示 -> 指标与导出复盘”的产品闭环。
- AI 结果用于正式医生判读前的辅助提示，帮助提示是否值得优先关注或转交复核。
- 固定样例和真实模型 smoke 证明部署链路可运行，不证明临床准确率。

禁止表达：

- 不说“自动临床诊断系统”“替代医生诊断”“最终诊断结论”。
- 不把固定样例回放、mock 回放或真实模型 smoke 写成医学效果验证。
- 不承诺患者管理、医生复核、权限审计、医院系统集成或教学训练模式已经实现。
- 不编造 accuracy、F1、recall、混淆矩阵或真实临床验证结论。

# 产品体验闭环专项说明

本文档定义“产品化优化阶段”的产品体验目标、用户洞察、价值假设、核心场景、解决方案和展示口径。它不是新的临床 PRD，也不替代 `docs/PRD.md`、`docs/TECH_DESIGN.md` 或 `docs/UI_REDESIGN.md`；后续 UI 状态、README 叙事和 Demo runbook 调整应优先与本文保持一致。

本轮不碰模型能力、不做训练评估、不做深层重构。优化重点是：把现有 ECG AI 辅助识别 Demo 从“能运行的工程样机”进一步整理成“围绕真实工作流和用户痛点设计的产品原型”。

## 1. 产品定位

当前产品原型定位为：

> 面向 ECG 采集、初筛和部署验证场景的 AI 辅助桌面工作台，通过固定样例回放或串口输入展示 ECG 波形、心率、导联状态、AI 辅助识别结果、运行指标和可追溯导出。

它要证明的不是“模型已经具备临床诊断能力”，而是：

- ECG 信号可以进入统一处理管线。
- 使用者可以在一个工作台中确认波形、导联、心率和运行状态。
- AI 模型结果可以作为正式判读前的辅助提示被清晰展示。
- 模型契约可以约束部署侧输入、归一化和标签语义。
- 运行过程可以被导出、回放和复盘。
- 产品已经具备从“算法产物”走向“可交互 Demo”的基本形态。

本阶段的产品化优化不等于临床产品落地。它仍是实验与展示原型，但设计逻辑应从真实使用场景出发，而不是从“给别人看 Demo”出发。

## 2. 真实工作流与最大价值假设

### 2.1 简化工作流

在现实 ECG 场景中，采集和正式诊断通常不是同一件事。一个简化流程可以理解为：

```text
医生开具 ECG 检查 / 患者进入采集场景
-> 采集人员贴电极、接导联、采集波形
-> 现场确认信号质量、导联状态和基础心率
-> 非心电专家或一线人员做初步风险判断和转交
-> 医生 / 心内科医生进行正式判读
-> 结果归档、复盘或进入后续处理
```

这里的关键摩擦在于：采集人员或基层初筛人员通常不承担最终诊断责任，但他们仍然要在现场判断“这段信号能不能看”“是否需要重采”“是否有明显异常提示需要优先交给医生”。这不是最终诊断，却会影响后续诊断效率和安全边界。

### 2.2 最大价值假设

本产品当前最大的价值假设是：

> 在 ECG 采集到医生正式判读之间，为非心电专家的一线人员提供一个“信号质量可见、基础状态清楚、AI 辅助提示可读、运行过程可追溯”的初筛工作台，降低现场判断、转交和后续复盘成本。

这个价值假设由四层组成：

1. **信号先可信**
   - 如果波形、导联和心率状态不可见，AI 结果再漂亮也缺少前提。
   - 所以中央波形、导联状态和心率卡不是辅助装饰，而是 AI 生效前的质量底座。

2. **AI 做第二观察者**
   - AI 结果不替代医生诊断，而是在正式判读前提供一个稳定、结构化的辅助提示。
   - 对基层医生、年轻医生或非心电专家来说，它的价值是帮助识别“这张图是否值得优先关注或复核”。

3. **状态帮助转交**
   - 当现场人员把 ECG 交给医生、研究人员或维护者时，不只交一张波形图，还能交出导联、心率、诊断次数、推理耗时和运行摘要。

4. **回放支撑复盘**
   - `ecg_replay.csv`、`diagnosis.csv` 和 `metrics.jsonl` 让一次运行可以被复现和讨论，而不是只停留在当场看到的 UI 结果。

因此，AI 功能的价值不是单独成立的；它和信号质量、状态反馈、导出复盘一起构成产品价值：

```text
可靠信号
-> AI 辅助识别
-> 初筛提示 / 转交复核
-> 医生正式判读
-> 导出与回放复盘
```

### 2.3 当前假设的边界

本价值假设仍需要未来真实用户访谈和场景验证。当前 Demo 可以支撑“产品逻辑和部署闭环”展示，但不能证明：

- AI 提示已经达到临床可用准确率。
- 现场人员可以依据 AI 输出直接处置患者。
- 医生复核流程、患者管理和合规审计已经完成。

## 3. 用户群体洞察

下面的用户洞察基于当前 PRD、系统能力和 ECG 上位机使用场景推导，属于产品假设。后续如果进入真实临床合作，应通过访谈、现场观察和任务验证进一步校准。

### 3.1 核心用户：ECG 采集与初筛人员

典型角色：

- 心电图室技师。
- 基层医院或社区场景中的全科 / 值班医生。
- 急诊、病房、床旁设备侧负责初步采集的医护人员。
- 需要先看 ECG、但不是心电专科医生的一线人员。

他们不是模型训练者，也不一定熟悉 AI 模型细节。他们更关心“当前这次采集是否可靠、有没有明显异常提示、是否需要优先转交医生、设备是否还在正常工作”。

核心任务：

- 确认 ECG 波形正在稳定输入。
- 判断导联连接是否正常，避免在导联脱落时继续采集无效信号。
- 快速读取心率等基础生命体征信息。
- 在 ECG 片段达到推理窗口后看到 AI 辅助识别提示。
- 根据提示决定是否需要重采、优先转交医生或继续观察。
- 需要时保留本次运行结果，便于交给后续医生、研究人员或维护者复盘。

痛点：

- 他们不负责最终诊断，但常常承担“这张 ECG 是否值得优先关注”的前置判断压力。
- ECG 波形、导联状态、心率和辅助识别如果分散在多个区域，现场人员很难快速判断“现在能不能继续看”。
- 导联脱落、接触不良或样本不足如果提示不清楚，容易被误以为是模型无结果或系统故障。
- AI 输出如果写得过强，会让一线使用者误以为系统给出了最终诊断；如果写得过弱，又看不出模型辅助价值。
- 采集结束后如果没有摘要和导出，后续很难复盘“这次运行到底发生了什么”。

产品机会：

- 把“波形可见、导联可用、心率可读、AI 有辅助提示、运行可追溯”合成一条工作台体验。
- 用状态文案告诉用户当前系统处于哪一步，降低对菜单和日志的依赖。
- 把 AI 结果明确标注为辅助识别，让它成为“提示和转交依据”，而不是“最终诊断结论”。

### 3.2 重要次级用户：临床研究人员 / 算法验证协作者

典型角色：

- 做 ECG 算法验证的研究人员。
- 负责模型部署验证的算法或工程同学。
- 需要复盘模型输入、输出和运行日志的项目成员。

他们关注的不是单次操作是否顺手，而是“这条链路是否可复现、可验证、可追踪”。

核心任务：

- 使用固定样例或最近导出文件进行离线回放。
- 查看源标签、本次辅助识别结果、诊断次数和推理耗时。
- 确认真实模型和 mock 回放路径都能工作。
- 通过 `metrics.jsonl`、`diagnosis.csv`、`ecg_replay.csv` 复盘一次运行。
- 判断模型契约是否与部署输入、标签顺序和 UI 展示一致。

痛点：

- 如果 Demo 依赖临场手工选择数据，结果很容易不可复现。
- 如果 UI 只展示最终标签，不展示运行指标和导出路径，研究人员难以判断链路是否真的跑通。
- 如果训练侧模型信息和部署侧 UI 标签分离，容易出现“模型输出与界面解释不一致”的风险。

产品机会：

- 固定 Demo 场景让验证过程稳定复现。
- 模型契约让模型语义不散落在 UI 或临时脚本里。
- 运行摘要和导出文件让 Demo 不只是视觉展示，也能变成一次可追踪的实验记录。

### 3.3 采购 / 合作 / 评审决策者

典型角色：

- 科室负责人。
- 项目评审老师或合作方。
- 潜在首批客户中的技术或业务负责人。
- 公开展示读者或项目评审者。

他们通常不是日常操作用户，但会判断这个产品原型是否有真实场景、清晰边界和继续投入价值。

核心关注：

- 这个产品面向谁，解决什么实际问题。
- 现有 Demo 能不能完整跑通，而不是停留在模型或论文层面。
- AI 输出是否边界清晰，不会被包装成未经验证的临床诊断。
- 技术链路是否可维护：模型契约、处理管线、导出、回放是否形成闭环。
- 后续如果继续做，应该补齐哪些临床、评估和合规能力。

痛点：

- 很多 AI 医疗 Demo 容易只展示模型结果，缺少采集、状态、导出和复盘闭环。
- 如果只讲算法，不讲实际使用场景，决策者难以判断产品价值。
- 如果过度包装临床能力，会降低可信度。

产品机会：

- 用一条固定体验旅程展示产品思路：采集 / 回放 -> 波形 -> 状态 -> AI 辅助识别 -> 指标 -> 摘要 / 导出。
- 用克制文案说明边界，让产品显得更可信。
- 把 Demo 定位为“首版可交互原型”，为后续真实用户验证留出空间。

### 3.4 未来潜在用户：ECG 学习与训练用户

典型角色：

- 新手医生。
- 医学生。
- 规培医生。
- 需要练习 ECG 判读的基层医生。

他们不是当前 V1 的主要用户，但当前“保存信号 + 离线回放 + 源标签 / 诊断结果对照”的能力，为未来训练模式提供了基础。

潜在痛点：

- ECG 学习依赖静态教材和零散病例，缺少可重复回放的动态波形练习。
- 新手医生常常不知道自己错在信号质量判断、节律判断，还是异常类型识别。
- 练习后缺少即时反馈、标准标签对照和错题复盘。

未来机会：

```text
历史 ECG 信号 / 样例库
-> 回放练习
-> 学员先做判断
-> AI 辅助提示 / 标准标签对照
-> 错题与难例复盘
-> 案例库沉淀
```

该方向需要新增题目模式、答案遮罩、标准解释、学习记录、难度标签和案例管理等能力，当前阶段只记录为未来产品机会，不进入本轮实现范围。

### 3.5 非核心用户

以下用户不是本阶段体验优化的主要对象：

- 患者本人：当前系统不提供患者端功能，也不展示面向患者解释的诊断报告。
- 医院信息科管理员：当前不涉及账号、权限、审计、HIS/EMR 集成或院内部署管理。
- 专职模型训练人员：训练侧能力是项目主线的一部分，但本轮产品体验优化不修改训练流程。

## 4. 核心用户与产品焦点

本阶段的核心用户应定义为：

> ECG 采集与初筛人员，尤其是需要在医生正式判读前进行信号确认、初步风险提示和转交的一线非心电专家用户。

原因：

- 他们最直接面对“波形是否有效、导联是否连接、心率是否可读、AI 提示是否出现”的工作流。
- 当前 PyQt 上位机的界面形态天然更接近设备侧工作台，而不是算法实验平台或管理后台。
- 他们的任务能够被现有 Demo 能力真实支撑，不需要新增数据库、患者管理或医生复核流程。
- 围绕他们设计体验，也能自然服务次级用户和评审对象：研究人员可复盘，决策者可理解场景价值。

本阶段不把“公开展示读者 / 领导 / 评审者”定义为产品核心用户。他们是产品展示的受众，不是产品日常使用者。

## 5. 用户痛点到解决方案

| 用户痛点 | 产品方案 | 当前 Demo 对应能力 |
| --- | --- | --- |
| 操作人员需要快速判断 ECG 是否正在有效输入 | 中央 ECG 波形作为主视觉，保持实时刷新和清晰网格背景 | `ecg1WaveLabel` 波形绘制 |
| 导联脱落会导致采集无效，但不一定能被立刻注意到 | 右侧导联状态卡显示三导联单通道状态，明确连接 / 脱落 / 未知 | `on_lead_status()`、导联状态控件 |
| 心率是高频查看信息，需要比普通文字更醒目 | 独立心率卡显示数值和单位，无效时显示 `--` | `on_heart_rate()` |
| 非心电专家不负责最终诊断，但需要识别是否值得优先转交 | AI 结果卡给出保守辅助识别提示，不写成最终结论 | `connectStateLabel_2`、`ui_rules.py` |
| AI 输出容易被误读成最终诊断 | 使用“AI 辅助识别 / 辅助提示”文案，并避免临床结论式措辞 | `connectStateLabel_2`、`ui_rules.py` |
| 用户不知道系统是否正在运行、是否完成 | 顶部模式和状态提示表达待机、运行、完成、异常 | 顶部状态区、Demo mode |
| 医生或研究人员需要复盘本次运行 | 底部指标、最近摘要和导出目录提供可追溯证据 | `WorkerMetrics`、`RunExporter` |
| 外部评审需要判断产品是否可交付 | 一键 Demo 和固定场景降低演示不确定性 | `run_demo.ps1`、`--demo`、固定 policy |

## 6. 当前能力与未来扩展矩阵

本节把核心用户痛点映射为当前已经提供的能力，以及未来可以在现有基础上扩展的方向。这里的未来扩展是产品机会，不是当前 V1 已实现能力。

### 6.1 需求证据线索

| 证据线索 | 对产品需求的启发 |
| --- | --- |
| ECG 检查通常由技术人员完成电极贴附和采集，结果由医疗提供者复核。参考 [MedlinePlus ECG 说明](https://medlineplus.gov/ency/article/003868.htm)。 | 采集人员位于“设备输入”和“医生正式判读”之间，产品应帮助其完成信号确认和转交，而不是让其承担最终诊断。 |
| EKG technician 职责中包含连接导联、监测患者、识别并纠正 wandering、interference 和 artifact。参考 [Cleveland Clinic EKG Technician](https://my.clevelandclinic.org/departments/heart/medical-professionals/careers/ekg-technician)。 | 信号质量、导联状态和伪差识别是核心用户的真实任务，不能只展示 AI 分类标签。 |
| ECG 技术错误、导联误放和伪差会影响解释，相关综述强调正确导联放置和识别 artifact 的重要性。参考 [Technical Mistakes during the Acquisition of the Electrocardiogram](https://pmc.ncbi.nlm.nih.gov/articles/PMC6932211/)。 | 产品应先保证“这段 ECG 能不能看”，再展示 AI 辅助结果；未来可扩展信号质量评分和伪差提示。 |
| 自动化 ECG 解读存在误差，文献强调 automated computerized ECG interpretations 需要医生 overread。参考 [Diagnostic accuracy of automated computerised electrocardiogram interpretation](https://ccforum.biomedcentral.com/articles/10.1186/cc5405)。 | AI 结果应定位为正式判读前辅助提示，必须保持“医生复核 / 不作最终诊断”的展示边界。 |

### 6.2 采集质量保障层

对应核心问题：采集人员首先要知道“这段信号能不能看”，否则后续 AI 输出缺少可信前提。

| 痛点 | 当前已提供能力 | 当前价值 | 未来可扩展方向 |
| --- | --- | --- | --- |
| 不知道 ECG 是否正在有效输入 | 中央 ECG 波形主视觉 | 让用户先观察真实波形，而不是直接相信 AI 标签 | 信号质量评分、采集质量灯 |
| 导联脱落或接触异常会导致无效采集 | 三导联单通道导联状态卡 | 明确导联连接 / 脱落 / 未知状态 | 导联接触质量、脱落时间统计 |
| 心率是现场高频查看信息 | 心率卡，无效状态显示 `--` | 帮助用户快速确认基础生命体征状态是否可读 | 心率趋势、异常波动提示 |
| 样本不足时不应强行出结果 | 按模型契约窗口累计到 2000 点后触发推理 | 避免短窗口误触发和结果误读 | 采集进度提示、窗口完成提示 |
| 新手采集时容易漏掉前置检查 | 当前未实现 | - | 采集前检查清单、电极 / 导联准备提示 |

### 6.3 AI 辅助识别层

对应核心问题：非心电专家不承担最终诊断，但需要一个正式判读前的结构化辅助提示。

| 痛点 | 当前已提供能力 | 当前价值 | 未来可扩展方向 |
| --- | --- | --- | --- |
| 非专科人员难以快速获得 ECG 异常线索 | AI 辅助识别结果卡 | 给出模型分类标签，作为正式判读前参考 | 结果解释卡、关注原因提示 |
| AI 输出容易被误读成最终结论 | “辅助识别 / 辅助提示 / 医生复核”文案 | 限制医学边界，避免过度信任 | 更清晰的结果边界说明、误用提示 |
| 模型输出语义可能和 UI 标签漂移 | 模型契约管理窗口、归一化和标签顺序 | 保证部署侧按契约解释模型输出 | 模型版本说明、契约变更提示 |
| 用户不知道模型是否真的执行过 | 诊断次数、单次推理耗时 | 显示推理链路发生过，并可用于复盘 | 多窗口连续结果趋势 |
| 用户需要理解模型不确定性 | 当前未实现 | - | 置信度 / 不确定性提示，但前提是先建立可靠评估基线 |

### 6.4 交接与复盘层

对应核心问题：一次 ECG 采集不应只留下一个结果标签，还应留下可交接、可复盘的运行证据。

| 痛点 | 当前已提供能力 | 当前价值 | 未来可扩展方向 |
| --- | --- | --- | --- |
| 本次运行发生了什么不清楚 | 最近运行摘要 | 汇总运行路径、诊断次数、最近结果和导出位置 | 结构化交接卡 |
| 医生或研究人员需要复盘输入 | `ecg_replay.csv` | 保存可回放 ECG 数据 | 多次运行列表、按时间检索 |
| 需要追踪 AI 输出事件 | `diagnosis.csv` | 记录诊断事件和结果 | 诊断事件时间线 |
| 需要证明系统处理过程 | `metrics.jsonl` | 记录指标快照、推理耗时和吞吐量 | 复盘时间线、运行质量报告 |
| 交给医生时缺少上下文 | 当前只提供摘要和导出 | 已能提供基础复盘材料，但还不是完整交接报告 | 医生复核备注、导出报告模板 |

### 6.5 验证、教学与能力演进层

对应未来机会：当前保存和回放能力可以支撑教学、验证和模型迭代，但这些都不是当前 V1。

| 未来方向 | 当前基础 | 潜在价值 | 边界 |
| --- | --- | --- | --- |
| ECG 回放训练模式 | 离线回放、源标签对照、AI 辅助提示 | 新手医生或基层医生先判断，再查看标准标签和辅助提示 | 当前未实现题目模式、答案遮罩和学习记录 |
| 案例库 | `ecg_replay.csv` 和固定 demo policy | 按类别沉淀可重复练习样例 | 需要独立案例管理设计 |
| 错题和难例复盘 | 诊断事件和源标签对照 | 帮助学习者或算法团队分析误判 | 需要用户身份、答题记录和标准解释 |
| 模型版本对比 | 模型契约和真实模型回放 | 同一条 ECG 对比不同模型输出 | 需要模型版本管理和评估基线 |
| 医生复核反馈 | 当前只保留运行摘要和导出 | 为产品闭环和模型迭代积累反馈 | 需要医生工作流、权限和审计设计 |

### 6.6 优先级判断

如果继续围绕当前产品原型演进，优先级建议如下：

| 优先级 | 功能方向 | 原因 |
| --- | --- | --- |
| P1 | 信号质量提示 / 采集质量灯 | 直接对应采集人员最基础的“这张 ECG 能不能看”问题。 |
| P1 | 结构化交接卡 / 运行摘要增强 | 当前已经有导出和摘要基础，投入小，产品价值清晰。 |
| P1 | AI 结果解释边界增强 | 继续强化“辅助提示，不是诊断”的产品可信度。 |
| P2 | 复盘时间线 | 可以把导联、心率、推理和指标事件串起来，增强可追溯性。 |
| P2 | ECG 回放训练模式 | 有离线回放基础，但需要独立题目、答案遮罩、学习记录和案例库设计。 |
| P3 | 医生复核反馈、模型版本对比、案例库治理 | 价值高，但依赖权限、数据管理、评估基线和更完整工作流。 |

## 7. 核心产品旅程

本阶段建议把体验闭环组织为一条 7 步主路径：

1. 启动固定场景
   - 使用一键脚本或 `python main.py --demo` 进入固定场景。
   - 用户看到系统处于 Demo / 离线回放状态，知道当前是在模拟一次可复现的 ECG 采集与初筛流程。

2. 确认信号输入
   - 中央 ECG 波形开始刷新。
   - 用户先判断当前是否有有效 ECG 信号，而不是直接相信 AI 输出。

3. 观察基础状态
   - 右侧显示心率和导联状态。
   - 用户确认导联是否连接、心率是否可读，避免把信号质量问题误当成模型问题。

4. 等待 AI 辅助识别
   - ECG 样本达到模型窗口后触发推理。
   - AI 结果卡显示辅助识别标签和保守提示文案。

5. 形成正式判读前的辅助提示
   - 用户把 AI 结果作为“是否需要优先关注或转交复核”的提示。
   - UI 不把它呈现为最终临床诊断或处置依据。

6. 查看运行证据
   - 底部显示包计数、诊断次数、推理耗时和吞吐量。
   - 最近摘要展示样例来源、诊断次数、最近结果和导出位置。
   - 用户知道系统不是只显示结果，而是在持续处理数据并留下复盘线索。

7. 导出与回放复盘
   - 查看 `metrics.jsonl`、`diagnosis.csv`、`ecg_replay.csv`。
   - 医生、研究或维护人员可以基于文件复盘本次运行。

这条路径同时服务三类人：核心用户完成信号确认和初筛观察，研究人员完成链路验证，决策者看到产品闭环。

## 8. UI 状态模型

本阶段 UI 状态模型只描述产品体验语义，不新增业务流程，也不改变 worker、pipeline、model contract 或导出逻辑。后续代码实现应优先复用现有状态入口和 slot。

| 状态 | 触发时机 | 用户看到的提示 | 用户下一步 |
| --- | --- | --- | --- |
| 未启动 / 串口待机 | 普通 `python main.py` 启动后，或停止采集 / 回放后回到待机 | 顶部显示 `串口待机`，提示 `在线采集 / 离线回放可用`，AI 结果和指标保持未开始状态 | 选择串口采集、离线回放，或使用一键 Demo 进入固定场景 |
| Demo 就绪 | `python main.py --demo` 预检通过，但自动回放尚未真正启动 | 顶部显示 `Demo 就绪`，展示固定 demo policy，提示 `预检通过 · 等待自动启动` | 等待自动启动，不需要手工点菜单 |
| 启动中 | Demo 或离线回放已经发起，worker 正在创建或载入数据 | 顶部显示 `Demo 启动中` 或 `离线回放启动中`，提示回放正在启动 | 等待波形开始刷新；如果长时间无变化，再查看异常提示 |
| 运行中 | 串口采集或离线回放已经开始，ECG 样本、心率、导联和 metrics 开始更新 | 顶部显示 `Demo 运行中`、`离线回放运行中` 或 `串口运行中`，中央波形和底部指标持续更新 | 先确认波形、导联和心率，再等待 AI 辅助识别结果 |
| 推理完成 | ECG 样本达到模型窗口并完成一次模型推理 | 右侧 AI 结果卡显示辅助识别标签，底部诊断次数和推理耗时更新；顶部可继续保持运行中 | 把结果理解为正式判读前的辅助提示，继续观察或准备查看摘要 |
| 已完成 | 离线回放或 Demo 回放结束，导出器完成本次运行记录 | 顶部显示 `Demo 已完成` 或 `离线回放已完成`，提示可查看最近运行摘要和导出文件 | 点击 `最近摘要` 复盘本次运行，必要时打开导出目录 |
| 异常 | Demo 预检失败、模型不可用、回放配置非法、worker 报错或串口异常 | 顶部或状态栏显示不可用 / 失败原因，必要时弹出阻断提示 | 根据提示检查模型契约、模型文件、样例数据、回放配置或依赖环境 |
| 重置后 | 用户点击 `重置显示`，清空当前波形缓存和展示状态 | 状态栏显示 `显示已重置`，波形、心率、导联、AI 结果和指标回到默认展示 | 重新启动离线回放、串口采集或 Demo |

状态设计边界：

- `推理完成` 不一定替代顶部主状态；它可以主要体现在 AI 结果卡和指标区，避免运行中状态被频繁打断。
- `异常` 只描述已有预检、模型、回放、串口和 worker 错误，不扩大异常处理范围。
- `重置后` 只清空展示状态，不改变 demo policy、模型契约、样例数据或导出文件结构。
- 所有状态文案都必须使用“辅助识别 / 辅助提示”口径，不写成最终诊断或临床处置建议。

## 9. 体验设计原则

- **先服务真实操作者，再服务展示观看者**：UI 首先回答采集和初筛人员“信号能不能看、结果是否出现、状态是否正常”，展示叙事建立在这个真实流程之上。
- **让 AI 做辅助提示，不做最终诊断**：AI 结果是正式判读前的第二观察者，帮助提示是否值得优先关注或复核。
- **信号质量是 AI 价值前提**：波形、导联和心率不是弱功能，而是保证 AI 提示有意义的前置条件。
- **让状态承担引导职责**：顶部状态、右侧卡片和底部指标共同解释系统当前阶段，减少用户猜测。
- **让导出承担可信职责**：运行产物证明链路可复盘，但不证明模型医学准确率。
- **固定 Demo 是产品验证手段**：固定样例不是为了回避真实场景，而是为了让产品流程可重复验证。
- **训练模式先作为未来机会**：ECG 回放可以演进为新手医生训练模块，但需要独立产品设计，不混入当前 V1。
- **不做超前产品化**：当前不引入患者管理、医生复核、权限审计和医院系统集成，避免原型失焦。

## 10. 当前体验构成

| 区域 | 面向用户问题 | 当前职责 |
| --- | --- | --- |
| 顶部模式与操作区 | 我现在处于什么模式？下一步能做什么？ | 展示 Demo / 离线回放 / 串口状态，提供回放、摘要、导出和重置入口。 |
| 中央 ECG 波形区 | 当前是否有有效 ECG 信号？ | 展示回放或串口输入的 ECG 波形，是第一视觉中心。 |
| 右侧 AI 结果卡 | 模型是否给出了辅助提示？是否值得优先关注或复核？ | 展示模型分类标签和边界说明。 |
| 右侧心率卡 | 当前心率是否可读？ | 展示心率数值，无效状态显示 `--`。 |
| 右侧导联状态卡 | 导联是否连接正常？ | 展示三导联单通道连接 / 脱落 / 未知状态。 |
| 底部指标区 | 系统是否真的在处理数据？ | 展示包计数、诊断次数、推理耗时、吞吐量和事件计数。 |
| 最近摘要 / 导出目录 | 本次运行如何复盘？ | 汇总最近运行并打开导出文件位置。 |

## 11. 展示口径

推荐表达：

- 这个产品原型面向 ECG 采集与初筛场景，帮助用户同时查看波形、导联、心率、AI 辅助识别和运行指标。
- 固定 Demo 用样例 ECG 回放模拟一次稳定的采集 / 初筛流程，用来展示产品闭环。
- AI 结果用于正式医生判读前的辅助提示，帮助提示是否值得优先关注或复核，不替代医生诊断。
- 模型契约用于约束输入窗口、归一化参数和标签顺序，避免模型语义在 UI 中漂移。
- CLI 回放、GUI 回放和串口输入进入同一条 ECG 处理管线，降低路径分叉。
- 导出文件用于复盘本次运行过程，包括指标、诊断事件和可回放 ECG 数据。
- 当前原型用于验证产品设计和部署链路，不等同于临床独立诊断系统。
- 未来可探索基于回放能力的新手医生 ECG 训练模块，但这属于后续产品方向。

禁止表达：

- 不能写成“临床诊断系统”“自动诊断医生”或“最终诊断结论”。
- 不能把固定样例 Demo、mock 回放或真实模型 smoke 写成医学准确率验证。
- 不能承诺真实医院部署、患者管理、医生复核、权限审计或临床合规能力。
- 不能把未来训练模式写成当前已实现能力。
- 不能编造 accuracy、F1、recall、混淆矩阵或真实临床效果。

## 12. 非目标

- 不训练新模型，不替换模型，不修改模型契约格式。
- 不补写或推断模型精度指标。
- 不修改 ECG 处理管线、推理触发、回放数据流或导出文件结构。
- 不引入 Web 后端、数据库、账户体系、患者管理或医院系统集成。
- 不新增真实临床数据采集、医生复核流程或审计能力。
- 不新增 ECG 教学训练模式、案例库、答案遮罩、错题记录或学习管理功能。

## 13. 验收标准

完成本轮产品化优化后，应能回答：

- **最大价值假设是什么**：在 ECG 采集到医生正式判读之间，提供信号质量可见、AI 辅助提示可读、运行过程可追溯的初筛工作台。
- **核心用户是谁**：ECG 采集与初筛人员，尤其是需要在正式判读前做信号确认、初步风险提示和转交的一线非心电专家用户。
- **次级用户是谁**：临床研究人员、算法 / 部署协作者；他们需要可复现回放、模型契约、指标和导出复盘。
- **展示对象是谁**：评审者、合作方、公开展示读者或潜在客户决策者；他们通过 Demo 判断产品场景、解决方案和边界是否成立。
- **解决什么问题**：把 ECG 输入、状态监测、AI 辅助识别、运行指标和导出复盘合成一条可讲、可跑、可验证的体验闭环。
- **为什么 AI 有价值**：AI 不替代诊断，而是在可靠信号基础上提供结构化辅助提示，帮助非专家用户识别是否需要优先关注或转交复核。
- **未来机会是什么**：基于保存和回放能力，后续可探索新手医生 ECG 训练模块，但当前不实现。
- **什么不做**：不扩张模型能力，不新增临床系统能力，不把演示验证包装成医学效果评估。

文档和 UI 后续变更应满足：

- README 先呈现真实产品场景、核心价值假设和体验闭环，再呈现技术支撑。
- Demo runbook 能按 5-7 步讲清启动、观察、辅助识别、指标、摘要和导出。
- 顶部状态文案、AI 结果说明、异常提示和重置后默认态都保持辅助识别边界。
- 自动化测试继续保护现有 Demo 主路径，不为了文案优化放宽核心行为。

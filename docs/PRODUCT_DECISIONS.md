# 产品决策记录

本文档轻量记录当前 ECG AI 辅助识别工作台 Demo 中最重要的产品取舍。它不是完整 ADR 体系，只保留项目展示、评审和后续维护时最容易被追问的决策。

## 1. 先做固定 Demo，而不是依赖真实设备

**背景**：真实串口设备和现场采集环境不稳定，演示时很容易受设备、驱动、连接状态和样本质量影响。

**选择**：使用固定样例、固定 row、固定样本数和一键脚本，让 Demo 稳定进入离线回放流程。

**放弃方案**：演示时优先连接真实设备，或现场手动选择样例数据。

**原因**：本阶段要证明的是产品体验闭环和部署链路可运行。固定 Demo 可以稳定展示波形、心率、导联、AI 辅助提示、指标和导出复盘，降低临场失败概率。

**风险**：固定样例不能代表真实临床环境，也不能证明真实设备长时间运行稳定。后续需要单独做真实设备和干净环境验证。

## 2. AI 结果只写“辅助提示”，不写“诊断结论”

**背景**：当前模型 smoke test 只能证明部署链路可用，项目尚未形成完整临床评估、医生复核和合规流程。

**选择**：UI、README、Demo 脚本统一使用“AI 辅助识别 / 辅助提示 / 正式判读前参考”口径。

**放弃方案**：把模型结果展示为“临床诊断”“最终诊断”或“处置建议”。

**原因**：在医学场景中，过度包装 AI 输出会降低可信度，也可能误导用户。当前产品价值应表达为正式医生判读前的第二观察者，而不是替代医生。

**风险**：表达过于克制时，AI 价值看起来不如“自动诊断”强。需要通过信号确认、状态反馈、摘要和导出复盘来说明 AI 在工作流中的真实价值。

## 3. 保留导出和回放复盘，而不是只展示 UI 结果

**背景**：一次 ECG Demo 如果只停留在界面瞬时结果，后续很难解释输入来源、推理事件和运行过程。

**选择**：每次运行导出 `metrics.jsonl`、`diagnosis.csv` 和 `ecg_replay.csv`，并提供最近摘要和导出目录入口。

**放弃方案**：只在界面上显示波形和结果，不保存运行产物。

**原因**：导出与回放让 Demo 成为可复盘证据：研究人员可以看输入和结果，维护人员可以看指标，展示对象可以看到闭环不是一张静态截图。

**风险**：导出文件仍是工程证据，不是临床报告。后续若要做医生交接，需要单独设计结构化报告、复核备注和权限审计。

## 4. 不优先展示模型准确率

**背景**：当前仓库有训练侧和部署侧闭环，但独立测试集指标、类别级 recall/F1、混淆矩阵和模型版本记录仍不完整。

**选择**：README 和 Demo 文档先强调产品流程、模型契约、真实模型回放和可追溯导出，不把模型准确率放到首屏。

**放弃方案**：用未完整记录的 accuracy 或单次回放结果包装模型能力。

**原因**：项目展示中，可信边界比漂亮但不稳的指标更重要。当前最强证据是“能把算法产物接入可运行产品原型”，而不是证明模型医学效果已经成熟。

**风险**：读者可能会追问模型效果。回答时应说明当前 smoke test 的含义，并把后续计划指向独立评估基线、类别级指标和模型版本记录。

## 5. 不做患者管理、医生复核和医院系统集成

**背景**：患者管理、医生复核、权限审计和 HIS/EMR 集成都是临床产品化必需能力，但它们会显著扩大数据模型、权限、安全和合规复杂度。

**选择**：当前 V1 聚焦本地 PyQt 工作台、固定 Demo、ECG 管线、辅助识别、运行指标和导出复盘。

**放弃方案**：为了展示完整医疗产品形态，提前加入患者列表、医生复核、账号权限或医院系统对接。

**原因**：本阶段的核心用户是 ECG 采集与初筛人员，核心目标是证明正式判读前的轻量辅助工作台是否成立。过早引入管理系统会稀释主线，并产生无法兑现的临床产品承诺。

**风险**：如果后续进入真实临床合作，这些能力必须重新纳入 PRD 和技术设计，不能直接沿用当前 Demo 的文件型存储和无权限模型。

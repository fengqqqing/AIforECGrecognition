# ECG 自动识别系统技术设计

## 1. 技术栈选择

### 1.1 当前 V1 技术栈

当前项目是桌面上位机与模型部署项目，不是 Web 系统，也没有独立后端服务或数据库。V1 的目标是形成 ECG 信号采集、实时推理、结果展示、运行导出和离线回放的闭环。

| 层级 | 当前选择 | 说明 |
| --- | --- | --- |
| 前端界面 | PyQt5 | 用于实现桌面 GUI、串口配置、实时波形、诊断结果、运行指标和回放设置。 |
| 后端逻辑 | 同进程 Python 模块 | GUI、串口采集、推理触发、导出和回放运行在同一个桌面进程内，通过模块边界解耦。 |
| 模型推理 | PyTorch / TorchScript | 训练侧导出 `.pt` 模型，部署侧通过 `torch.jit.load()` 加载并执行分类推理。 |
| 数据存储 | CSV / JSONL / 模型文件 | V1 不引入数据库，运行数据以文件形式落盘，便于离线验证和实验复现。 |
| 测试框架 | unittest + 独立 smoke check | 覆盖协议解析、推理接口、串口 worker、导出、回放和关键 UI 状态链路。 |

当前 V1 的“后端”不是独立服务，而是桌面应用内部的业务模块。这样可以降低部署复杂度，适合当前以算法验证和模型部署为重点的阶段。

### 1.2 未来临床产品化演进

若项目进入真实临床采集和多用户使用阶段，技术栈可以演进为分层架构：

| 层级 | 推荐方向 | 说明 |
| --- | --- | --- |
| 前端界面 | Web 工作站或医用桌面工作站 | 根据医院现场部署条件选择。Web 便于多终端访问，桌面端便于设备直连。 |
| API 服务 | Python Web 服务 | 提供采集会话、诊断结果、医生复核、模型版本和审计查询接口。 |
| 推理服务 | 独立 Python 推理服务 | 隔离模型加载、推理资源和模型版本管理，避免 GUI 或 API 直接耦合模型细节。 |
| 结构化数据库 | PostgreSQL | 存储患者、采集会话、诊断结果、医生复核、运行日志和审计记录。 |
| 文件/对象存储 | 本地文件系统或对象存储 | 存储原始 ECG 波形、导出文件、模型文件和较大的实验产物。 |

未来演进不能反向污染当前 V1。当前阶段不为了文档强行拆服务、不创建数据库、不设计迁移脚本。

## 2. 项目结构

当前项目按职责可以分为两个主要域：

```text
模型训练/ECG
  负责 ECG 数据处理、模型定义、训练、评估和模型导出。

模型部署pyqt/ECGMonitor
  负责桌面上位机 GUI、串口采集、实时推理、导出、离线回放和测试。
```

### 2.1 训练侧

`模型训练/ECG` 是算法训练域，负责从 ECG 数据到可部署模型文件的完整训练链路。训练侧不直接依赖部署侧 GUI，也不承担在线采集和界面展示职责。它的核心产物是可被部署侧加载的 `.pt` / `.pth` 模型，以及支撑模型可信度判断的评估结果。

当前训练侧可以拆成 6 个子模块：

| 子模块 | 当前相关文件/目录 | 职责 |
| --- | --- | --- |
| 数据来源 | `artifacts/training/ecg/raw_data/`, `artifacts/training/ecg/processed_data/` | 保存 MIT-BIH 等原始 ECG 数据和已经整理好的 CSV 样本。 |
| 数据处理 | `dataset.py`, `dataset_.py`, `generate_data.py`, `spilt.py` | 读取原始记录或 CSV，生成训练、验证、测试数据。 |
| 信号预处理 | `filter.py` | 对 ECG 信号做去噪等预处理。 |
| 模型定义 | `model.py` | 定义 CNN 分类模型结构。 |
| 训练流程 | `train.py` | 加载数据、归一化、训练模型、保存 checkpoint。 |
| 评估与导出 | `test.py`, `draw.py`, `pth_to_pt.py` | 计算混淆矩阵、ROC/AUC、分类指标，并导出 TorchScript 模型。 |

#### 2.1.1 当前训练数据流

当前训练侧存在两条数据链路：

```text
原始 ECG 数据链路：
artifacts/training/ecg/raw_data/*.dat / *.hea / *.atr
-> wfdb 读取
-> 小波/滤波去噪
-> 按 R 波位置截取片段
-> 生成样本与标签
-> 训练/测试

CSV 快速训练链路：
artifacts/training/ecg/processed_data/train.csv / test.csv
-> pandas 读取
-> reshape 为固定窗口
-> 归一化
-> TensorDataset / DataLoader
-> CNNModel 训练
-> 保存 best_acc.pth / last.pth / epoch_xx.pth
-> 导出 best_acc.pt
```

后续训练优化应优先统一“训练输入窗口”和“部署输入窗口”的定义。部署侧当前模型输入为 `(B, 1, 2000)`，因此训练侧用于最终部署的主链路也应明确以 2000 点窗口为标准，避免训练样本和部署推理窗口不一致。

#### 2.1.2 模型训练职责边界

训练侧应该负责：

- 数据集读取和划分。
- ECG 预处理和归一化。
- 样本窗口生成。
- 标签体系定义。
- 模型结构定义。
- 训练超参数管理。
- checkpoint 保存。
- 指标评估。
- TorchScript 导出。

训练侧不应该负责：

- PyQt 界面展示。
- 串口协议解析。
- 在线 worker 生命周期管理。
- GUI 离线回放入口。
- 医生复核流程。
- 临床病例管理。

#### 2.1.3 后续模型精度优化方向

由于当前模型精度仍有提升空间，训练侧后续优化应优先围绕以下方向展开：

1. 数据质量与标签体系

- 明确当前分类数量、类别含义和标签映射。
- 检查各类别样本数量是否严重不均衡。
- 固化训练集、验证集、测试集划分，避免数据泄漏。
- 保留独立测试集，不参与调参。
- 记录每次训练使用的数据版本。

2. 输入窗口与预处理

- 统一训练和部署的窗口长度。
- 明确归一化参数来源，避免训练和推理使用不同尺度。
- 比较原始信号、去噪信号、标准化信号对模型效果的影响。
- 评估是否需要加入基线漂移处理、异常值裁剪或数据增强。

3. 模型结构

- 当前 CNN 是轻量 1D 卷积模型，适合部署验证。
- 后续可比较更深的 1D CNN、Residual CNN、CNN + Attention、CNN + BiLSTM 等结构。
- 模型优化必须同时关注精度、推理耗时和部署兼容性。
- 不建议一开始追求复杂模型，应先建立稳定评估体系。

4. 训练策略

- 引入类别权重或重采样处理类别不均衡。
- 增加学习率调度、早停、固定随机种子。
- 保存最优模型时同时记录验证指标。
- 每次训练输出训练配置、模型版本和指标摘要。
- 将 `best_acc` 从单一准确率逐步扩展为 macro-F1、recall、混淆矩阵等指标组合。

5. 评估体系

- 除整体 accuracy 外，必须关注每个类别的 precision、recall、F1。
- 对临床高风险类别，应优先关注召回率。
- 混淆矩阵应成为每次模型迭代的固定产物。
- 导出部署模型前，应运行独立测试集评估。
- 部署侧真实模型回放结果应反向反馈训练侧。

#### 2.1.4 训练产物管理

训练侧建议形成以下产物约定：

| 产物 | 说明 |
| --- | --- |
| `best_acc.pth` | PyTorch 权重文件，用于继续训练或评估。 |
| `last.pth` | 最后一个 epoch 的权重文件，用于断点分析。 |
| `epoch_xx.pth` | 阶段性 checkpoint，用于回溯训练过程。 |
| `best_acc.pt` | TorchScript 部署模型，供部署侧加载。 |
| 训练曲线 | loss、accuracy 等训练过程可视化结果。 |
| 评估报告 | 混淆矩阵、分类指标、ROC/AUC 等结果。 |

未来建议新增实验记录文件，至少记录：

- 数据集版本。
- 窗口长度。
- 归一化方式。
- 模型结构版本。
- 训练超参数。
- 最优 epoch。
- 验证集指标。
- 测试集指标。
- 导出的模型文件路径。

#### 2.1.5 与部署侧的契约

训练侧交付给部署侧的模型必须满足以下契约：

- 输入 shape 与部署侧一致，例如 `(B, 1, 2000)`。
- 输出类别数量与部署侧模型契约中的 `output.labels` 一致。
- 标签编号含义稳定，不允许训练侧和 UI 展示侧各自定义。
- 推理前归一化方式与训练时一致。
- 导出的 `.pt` 文件能在 Windows 中文路径下被部署侧加载。
- 模型推理耗时应满足上位机实时展示要求。

训练侧导出 `.pt` 后应同步提供契约信息，字段名称与部署侧 V1 契约保持一致。当前约定模板位于 `artifacts/training/ecg/models/contract_template.json`。训练侧必须记录输入窗口、输入 shape、归一化参数来源、标签编号与含义、输出类别数、checkpoint 来源、训练数据说明和测试集指标摘要；未知信息必须留空或说明“当前未记录”，不能伪造成事实。当前任务只补充约定，不修改训练脚本行为，也不自动生成契约。

#### 2.1.6 当前模型契约事实与接入状态

当前默认模型契约事实为：默认模型为 `模型部署pyqt/ECGMonitor/models/best_acc.pt`，输入窗口为 `2000`，推理输入 shape 为 `(B, 1, 2000)`，归一化参数为 `min_val=1582.0` 和 `max_val=2444.0`，输出类别数为 12，标签顺序来自 `best_acc.contract.json`，运行方式为 TorchScript / CPU。

这些事实已经整理到 `docs/MODEL_CONTRACT.md`，V1 格式定义见 `模型部署pyqt/ECGMonitor/models/model_contract.schema.md`。当前默认模型配套契约文件为 `模型部署pyqt/ECGMonitor/models/best_acc.contract.json`。

部署侧当前已经通过 `MODEL_CONTRACT_PATH` 读取契约，并将契约中的 `model_file`、`input.window_size`、`preprocessing.min_val`、`preprocessing.max_val` 用于推理，将契约中的 `output.labels` 用于 UI 标签展示。启动 warmup 阶段会检查契约文件、模型文件、标签数量、归一化参数，并通过 dummy input 验证模型输出类别数与契约一致。

`config.py` 当前只保留契约路径和运行环境配置；模型文件、窗口长度、归一化参数和标签顺序由模型契约提供，避免模型语义双源漂移。

### 2.2 部署侧

`模型部署pyqt/ECGMonitor` 是上位机与部署域，主要职责包括：

- `ParamMonitor`：主窗口协调层，负责 UI 事件、状态展示、串口 worker 生命周期和回放入口。
- `serial_worker`：实时串口 worker，负责串口打开、读取、字节解包、线程退出和 Qt 信号转发。
- `ecg_pipeline`：ECG 处理管线，负责 ECG 窗口累计、推理触发、导联/心率事件处理和 metrics 更新。
- `example`：模型推理边界，负责加载 TorchScript 模型、处理输入窗口并返回分类结果。
- `run_exporter`：运行产物导出层，负责写入指标、诊断事件和可回放 ECG 文件。
- `offline_replay` / `offline_replay_worker`：离线回放入口，负责读取回放数据和节奏控制，并把事件交给 ECG 处理管线。
- `replay_utils`：回放源解析公共逻辑，供 CLI 和 GUI 共同使用。
- `ui_rules` / `worker_metrics`：展示规则和运行指标格式化，避免 UI 与业务状态判断过度耦合。
- `tests`：回归测试与 smoke check，保护协议、推理、导出、回放和 UI 状态链路。

#### 2.2.1 当前 ECG 处理管线边界

当前 ECG 处理逻辑已经收敛到 `EcgProcessingPipeline`。`SerialInferenceWorker` 保留串口打开、读取、字节解包、线程退出和 Qt 信号转发职责；`OfflineReplayWorker` 和 `offline_replay.py` 负责读取回放数据和节奏控制，并直接使用同一条管线。`SerialInferenceWorker._process_packet()` 只作为 worker 内部薄包装，不再是离线回放或其他模块的共享处理入口。

管线必须保持以下行为不变：

- 仅处理包头 `packet[0] == 0x10` 的数据包；其他包直接忽略。
- 每处理一个 `0x10` 包，`metrics.total_packets` 增加 1。
- ECG 包使用子类型 `0x02`。采样值由 `packet[2] << 8 | packet[3]` 合成，并通过 `ecg_sample` 信号发出。
- ECG 包会让 `metrics.ecg_packets` 增加 1，并刷新运行时指标。
- ECG 采样点追加到当前诊断窗口；窗口长度来自模型契约 `input.window_size`。
- 当窗口累计达到契约窗口长度后，调用注入的 `predict_func` 触发推理。
- 推理成功后，记录单次推理耗时到 `metrics.last_inference_ms`，`metrics.diagnosis_count` 增加 1，刷新运行时指标，发出 `diagnosis` 信号，并立即发出一次 `metrics_updated` 快照。
- 推理失败时，记录日志并通过 `error` 信号发出 `AI推理失败: ...`。
- 无论推理成功或失败，达到窗口长度后的 ECG 窗口都会被清空。
- 如果 ECG 包未达到窗口长度，且 `metrics.ecg_packets` 是 `METRICS_EMIT_INTERVAL` 的整数倍，会发出一次 `metrics_updated` 快照。
- 导联包使用子类型 `0x03`。处理时 `metrics.lead_events` 增加 1，刷新运行时指标，发出 `lead_status` 信号，并发出一次 `metrics_updated` 快照。
- 导联状态为 `1` 表示导联脱落；此时会清空当前 ECG 诊断窗口。
- 心率包使用子类型 `0x04`。处理时 `metrics.heart_rate_events` 增加 1，刷新运行时指标。心率值由 `packet[2] << 8 | packet[3]` 合成，且只有 `hr > 0` 时才发出 `heart_rate` 信号和一次 `metrics_updated` 快照。
- `SerialInferenceWorker.run()` 退出时会刷新运行时指标、关闭串口、记录最终指标、发出最终 `metrics_updated` 快照，并发出 `closed` 信号。

调用方边界如下：

- `SerialInferenceWorker` 将管线回调连接到 `ecg_sample`、`diagnosis`、`lead_status`、`heart_rate`、`metrics_updated` 和 `error` 信号。
- `OfflineReplayWorker` 读取 CSV 后把 ECG、导联和心率事件注入管线，并把管线回调转为自身 Qt 信号。
- `offline_replay.py` CLI 读取同一套回放源解析逻辑后把事件注入管线；mock 模式使用固定标签函数，`--real-model` 使用真实 `predict()`。
- 后续离线回放不得再通过 `SerialInferenceWorker._process_packet()` 复用处理逻辑。

### 2.3 长期结构原则

- 训练侧和部署侧通过模型文件衔接，不互相反向依赖。
- GUI 负责展示和调度，不直接承担协议解析、模型加载和数据导出细节。
- CLI 回放和 GUI 回放必须共用回放源解析逻辑，避免行为分叉。
- 新增功能应优先复用现有模块边界，而不是把逻辑继续堆入主窗口类。
- 导出、离线回放和真实模型推理是当前最重要的验证闭环，后续改动必须优先保护。

## 3. 数据模型

### 3.1 当前 V1 数据对象

当前 V1 不建立数据库，主要数据对象以文件和内存状态存在：

| 数据对象 | 当前承载形式 | 说明 |
| --- | --- | --- |
| ECG 采样点 | 内存缓冲 + `ecg_replay.csv` | 串口或回放输入的原始波形点，达到窗口长度后用于模型推理。 |
| 诊断结果 | Qt 信号 + `diagnosis.csv` | 模型输出的分类结果及其展示标签。 |
| 运行指标 | 内存状态 + `metrics.jsonl` | 包括运行时长、诊断次数、单次推理耗时和吞吐量。 |
| 回放数据 | `sample_data/test.csv` / `runs/*/ecg_replay.csv` | 用于无设备环境下复用 ECG 波形进行验证。 |
| 训练数据 | `artifacts/training/ecg/raw_data/` / `artifacts/training/ecg/processed_data/` | 原始 ECG 记录和整理后的训练、验证、测试 CSV 样本。 |
| 模型文件 | `.pt` / `.pth` | 训练产物和部署推理文件。 |
| 评估产物 | 图片、控制台指标、后续实验记录 | 包括训练曲线、混淆矩阵、分类指标、ROC/AUC 等模型评估信息。 |
| 配置参数 | `config.py` | 包括窗口长度、模型路径、导出策略、回放策略和 UI 限制。 |

当前导出文件职责如下：

- `metrics.jsonl`：一行一个运行指标快照，便于增量写入和后续分析。
- `diagnosis.csv`：记录诊断事件、诊断标签、诊断次数、推理耗时和吞吐量。
- `ecg_replay.csv`：保存可回放 ECG 波形，并在末尾附带最近一次诊断结果作为源标签。

训练侧产物职责如下：

- `artifacts/training/ecg/processed_data/train.csv` / `test.csv`：当前 2000 点窗口训练和测试数据来源。
- `模型部署pyqt/ECGMonitor/sample_data/test.csv`：部署侧离线回放和 smoke test 的默认样例数据。
- `artifacts/training/ecg/models/*.pth`：训练过程中的 PyTorch 权重 checkpoint。
- `artifacts/training/ecg/models/*.pt`：训练侧导出的 TorchScript 模型文件。
- `模型部署pyqt/ECGMonitor/models/best_acc.pt`：部署侧默认加载的 TorchScript 模型文件。
- `artifacts/training/ecg/figures/*.png`：训练曲线等可视化结果。
- 后续实验记录：建议新增独立记录文件，保存数据版本、模型版本、训练参数和评估指标。

### 3.2 未来临床版数据实体

若进入临床产品化阶段，需要引入结构化数据模型，建议至少包含：

| 实体 | 说明 |
| --- | --- |
| Patient | 患者基本信息。需要脱敏、授权和访问控制。 |
| AcquisitionSession | 一次 ECG 采集会话，记录设备、时间、操作者和采集状态。 |

| DiagnosisResult | 模型输出结果、置信度、推理时间和关联模型版本。 |
| DoctorReview | 医生复核结论、修正意见和确认时间。 |
| RuntimeLog | 运行指标、异常、性能和设备状态。 |
| AuditLog | 用户访问、数据查看、结果修改和导出行为审计。 |

未来临床数据库只作为演进方向。V1 不保存真实患者身份信息，不建立完整病例库，也不承诺独立临床诊断。

## 4. 关键技术点

### 4.1 训练侧精度优化与实验可追溯性

训练侧后续优化的首要目标不是立刻更换复杂模型，而是先建立稳定、可复现、可比较的实验体系。每一次模型优化都应能回答：使用了哪一版数据、哪一种窗口和预处理方式、哪一个模型结构、哪些训练参数、最终在哪些指标上提升或退化。

后续训练改动应优先满足以下要求：

- 固定训练集、验证集、测试集划分，避免同一来源样本在训练和测试之间泄漏。
- 明确 12 分类标签编号与医学含义，并与部署侧展示标签保持一致。
- 将训练和部署的输入窗口统一到同一标准，当前部署侧主契约为 `(B, 1, 2000)`。
- 归一化参数必须可追溯，并保证训练侧和推理侧使用一致尺度。
- 每次训练至少输出 accuracy、macro-F1、各类别 recall、混淆矩阵。
- 对临床风险较高类别，优先关注召回率和误判方向，而不是只看整体准确率。
- 模型升级必须同时比较推理耗时，避免精度提升以明显破坏实时性为代价。
- 导出 `.pt` 前必须经过独立测试集评估，并记录对应 `.pth` 权重来源。

推荐的模型优化顺序：

```text
数据与标签检查
-> 固定评估基线
-> 处理类别不均衡
-> 调整训练策略
-> 小幅模型结构升级
-> 部署侧真实模型回放验证
```

不建议在没有评估基线时直接引入复杂结构。否则即使指标变化，也很难判断提升来自模型结构、数据划分、预处理变化还是测试集泄漏。

### 4.2 模型加载与路径兼容

部署环境包含 Windows 和中文路径，模型加载不能依赖对路径编码敏感的直接加载方式。当前部署侧应保持“先读取模型二进制，再通过内存流交给 `torch.jit.load()`”的方式，以降低中文路径导致模型加载失败的风险。

### 4.3 实时采集与线程稳定性

串口采集、推理触发和 UI 展示之间通过 PyQt 信号通信。线程退出必须被显式管理，避免窗口关闭时出现 `QThread: Destroyed while thread is still running`。后续所有涉及 worker 生命周期的改动都应覆盖启动、停止、异常退出和窗口关闭场景。

### 4.4 推理窗口、吞吐量与 UI 刷新

当前模型输入依赖固定 ECG 窗口长度。系统需要在以下目标之间保持平衡：

- 累计足够样本以满足模型输入。
- 控制单次推理耗时，避免阻塞 UI。
- 周期性刷新运行指标，让用户能看到系统仍在工作。
- 避免过高频率刷新导致界面卡顿或日志膨胀。
- 与训练侧保持相同窗口长度和归一化语义，避免部署结果和离线评估脱节。

### 4.5 导出与回放闭环

导出、回放和真实模型推理构成当前项目最关键的验证闭环：

```text
在线采集 -> 导出 ecg_replay.csv -> 离线回放 -> 真实模型推理 -> 结果对照
```

mock 推理适合稳定测试和无模型环境下的流程验证，但不能替代真实模型回放。涉及 `RunExporter`、`replay_utils`、`offline_replay`、`OfflineReplayWorker` 或 `SerialInferenceWorker` 的改动，都必须确认这个闭环没有被破坏。

### 4.6 医生辅助边界

系统定位为医生辅助识别工具。模型结果应被视为辅助提示，不能直接替代医生诊断。进入临床产品化前，需要补齐：

- 患者数据脱敏和授权管理。
- 用户权限和访问控制。
- 诊断结果的医生确认流程。
- 模型版本追踪和结果可追溯性。
- 数据访问、修改、导出和复核的审计记录。
- 真实临床采集的数据质量控制和异常处理。

## 5. 设计约束

- 当前 V1 不引入独立 Web 后端。
- 当前 V1 不引入数据库。
- 当前 V1 不保存真实患者身份信息。
- 当前 V1 不做完整病例管理。
- 当前 V1 不对外承诺自动临床诊断能力。
- 未来临床版设计只能作为演进方向，不能要求当前代码立即迁移。

## 6. 文档维护原则

- 当模型输入窗口、导出文件格式、回放策略或模块边界发生变化时，应同步更新本文档。
- 当项目决定引入真实临床采集、数据库或后端服务时，应先更新 PRD 和技术设计，再进入实现。
- 架构文档应描述事实和决策，不应把尚未实现的能力写成当前能力。
